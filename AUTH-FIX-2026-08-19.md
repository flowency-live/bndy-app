## Root causes

There are two separate faults plus one stale deploy.

### Fault 1: absolute API host on authed calls (the 401)

The session cookie is scoped to `.bndy.live`. Any call to `https://api.bndy.co.uk` from bndy.live is cross-origin and carries NO cookie. Four client modules still hard-coded the absolute host after the same-origin migration (commit 66c341f patched the other modules only):

- `src/lib/curator.ts`  ← the save-artist 401
- `src/lib/flags.ts`
- `src/lib/uploadImage.ts`
- `src/lib/artistTaxonomy.ts`

### Fault 2: routes outside /api on same-origin calls (the 404s)

CloudFront on bndy.live forwards ONLY `/api/*` and `/auth/*` to API Gateway. The users and uploads routes are registered WITHOUT the /api prefix (`/users/profile`, `/users/favourites`, `/uploads/presigned-url`). Same-origin calls to them hit the Next app and 404. This breaks the profile and favourites reads in AuthProvider, which is the "unstable login" feeling.

### Stale deploy

`GET /api/artists/taxonomy` 404s in production because the deployed artists-lambda predates the route. The local serverless repo was 95 commits behind origin/master when checked.
